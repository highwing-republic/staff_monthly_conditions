# スタッフスキル5段階追加設計書 v1.0
## 対象：ホテル清掃スタッフ月間シフト自動作成アプリ MVP

---

# 1. 目的

既存のスタッフ属性（スタッフ名、ロール、1日勤務時間、最大連続勤務日数、通常勤務可能曜日 等）に、
**清掃業務におけるスタッフのスキルレベル**を5段階で登録できるようにする。

# 2. 今回の追加範囲

スタッフごとのスキルレベル（1〜5）のみ。MVPでは登録・編集・保存・一覧表示まで対応する。

# 3. 今回は実装しないこと

スキル値は現時点では **OR-Toolsのシフト最適化条件には使用しない。**
（スキル5のスタッフを毎日1人入れる、平均スキル3以上、高稼働日は熟練者を増やす、新人同士だけにしない 等は対象外。将来拡張。）

# 4. ロールとスキルの違い

両者は別属性として扱う。

- ロール：スタッフが担当する役割（LEADER / CHECKER / CLEANER）
- スキル：清掃業務に対する熟練度（1〜5）

# 5. スキル定義

| レベル | 名称 | 目安 |
|---:|---|---|
| 1 | 初心者 | 入社直後・指導が必要 |
| 2 | 初級 | 基本作業を一部単独で行える |
| 3 | 標準 | 通常業務を安定して行える |
| 4 | 上級 | 高い品質・速度で作業できる |
| 5 | 熟練 | 非常に高い技能・指導可能 |

内部値は1〜5の整数のみ保持する。名称はUI表示用。

# 6. 重要方針

スキルは **清掃業務全般の総合スキル** として1つだけ持つ。
技能別（ベッドメイク、浴室清掃、速度、品質、新人指導力、チェッカー能力 等）の細分化は将来機能。

# 7〜11. DB変更・移行

- `staff` テーブルへ `skill_level INTEGER NOT NULL DEFAULT 3` を追加（CHECK `skill_level BETWEEN 1 AND 5` は任意）。
- 既存スタッフは `skill_level = 3`（標準）。既存データを削除・再作成しない。
- 移行は冪等：列がなければ `ALTER TABLE staff ADD COLUMN ...`、あれば何もしない。起動のたびに実行されてもエラーにしない。

# 12. Model変更

スタッフモデルへ `skill_level: int` を追加する。

# 13〜14. Validation

- 登録・更新時に `1 <= skill_level <= 5` を確認し、範囲外は「スキルは1〜5で入力してください。」と表示する。
- 新規スタッフで未設定は許可しない。UI初期値は3。

# 15〜18. Repository変更

`list_staff` / `get_staff` / `create_staff` / `update_staff` のすべてで `skill_level` を扱う。

# 19〜24. スタッフ管理UI

- 新規登録・編集にスキルを追加。selectbox（`1 - 初心者` 〜 `5 - 熟練`、初期値 `3 - 標準`）を推奨。
- 一覧に「スキル」列を追加（`5 - 熟練` 形式の表示も可）。
- 編集後は即座に staff テーブルへ保存する。

# 25〜28. シフト生成への影響

- `scheduler.py` のロジックは変更しない。Hard/Soft Constraint、目的関数、Precheck、Schedule Validation のいずれにも使用しない。
- SchedulerInput に skill_level が含まれても scheduler.py で参照しない。
- 理由：必要な熟練者数、平均スキル、高稼働日の条件、ロールとの優先関係、新人教育との関係が未決定のため。

# 29〜30. Excel出力

- スタッフ集計シートへ「スキル」列を追加することを推奨。
- 月間シフトシートのスタッフ名付近へのロール・スキル表示は任意。

# 31. テスト

- TEST01 / TEST02：skill_level = 1 / 5 を保存できる
- TEST03 / TEST04：skill_level = 0 / 6 を validation で拒否
- TEST05：既存スタッフの skill_level を変更できる
- TEST06：一覧取得時に skill_level が返る
- TEST07：既存DB移行後、既存スタッフの skill_level が 3 になる
- TEST08：移行を2回実行しても失敗しない
- TEST09：スキル追加前後で Solver の Hard Constraint 挙動が変わらない

# 32. 実装分割

SK01 Constants（SKILL_LEVELS）/ SK02 Model / SK03 DB Migration / SK04 Validation / SK05 Repository /
SK06 Staff List UI / SK07 Staff Create UI / SK08 Staff Edit UI / SK09 Excel / SK10 Regression Test

# 33. 実装時の禁止事項

スキルによるシフト優先、平均スキル制約、新人配置制約、高稼働日の熟練者制約、スキル別必要人数、
スキルによる所定勤務時間変更は追加しない。

# 34〜39. 将来Phase 2候補（今回は実装しない）

- 日別最低スキル合計（例：必要人数8人でスキル合計 >= 24）
- A：平均スキル（Solver上は除算を避け「スキル合計 >= 必要人数 × 3」に変換）
- B：熟練者最低人数（skill_level >= 4 を毎日2人以上）
- C：高稼働日条件（稼働率90%以上の日だけ skill_level >= 4 を2名以上）
- D：新人サポート（skill_level = 1 が勤務する日は skill_level >= 4 を1名以上）

まずスキル値を登録・蓄積し、現場でシフト品質に使えるかを確認する。

# 40. 完成条件

- スタッフ新規登録時にスキル1〜5を選べる
- 既存スタッフのスキルを変更できる
- 一覧でスキルを確認できる
- DBへ保存される
- 既存スタッフは初期値3
- 1未満・5超を拒否
- 既存シフト最適化には影響しない
- 既存テストが壊れない

# 41. 最終設計原則

ロールは **何を担当できるか**、スキルは **どの程度の熟練度か** を表し、分離して保持する。
今回はスキルをスタッフ属性として蓄積するだけにし、最適化への利用は実データと運用を確認してから追加する。
